# /merge — finish one feature (rules/ui.md W5, rules/worktrees.md W8)

0. A CLOSE CASE report instead of DONE PASS? → run `/close-case` first. Finished → it sends you back here to continue. Unfinished → it decides finish first or close now.

1. Read the task manager's done report. No click path while FLOW CHECK or UI CHECK is planned → bounce it: "no E2E script, not done". No TIME line with work and wait apart, or no FACTS line → bounce it: "no TIME, not done".
   Then, in the task's worktree: `${CLAUDE_PLUGIN_ROOT}/bin/agent-level.sh check --base origin/<working branch>` (R8; the production branch for a task with target production). It prints the blocks the real diff triggers. The task manager's pass lines (`agent-file.sh check`) cover them; a block the builder owns with no pass line → bounce it. PR REVIEW, CORE REVIEW, FLOW CHECK and UI CHECK are checked by the gate after the reviewer and the check deputy ran.
2. First run `${CLAUDE_PLUGIN_ROOT}/bin/agent-file.sh todo stage "<name>" e2e`. After DONE PASS: you launch the reviewer yourself (only a reviewer launched by the main manager counts): `Agent` with `subagent_type: reviewer`, the model and the effort of the Reviewer model setting (`${CLAUDE_PLUGIN_ROOT}/bin/agent-settings.sh get reviewer_model`, form model:effort; `python3 ${CLAUDE_PLUGIN_ROOT}/bin/agent_conf.py cli-model '<value>'` gives the `model`, the part after the colon goes into the `effort` field), description `<name> Review`, brief `[<model> <effort>]` first, then the task, `head: <sha>` (`git -C <worktree path> rev-parse HEAD`, or `git rev-parse origin/<branch>` for another machine), the approved requirement, the worktree path and the base: it does the PR REVIEW (and the CORE REVIEW when planned) and writes its line with `agent-file.sh check`. A fail → a fix order to the builder (where, what is seen, what is expected, evidence), stop here. Then, only when what the user sees or does changed, FLOW CHECK and UI CHECK of the task go to a check deputy that you launch yourself (only one launched by the main manager counts), one at a time on the browser: `Agent` with `subagent_type: check-deputy`, description `<name> Check`, brief `[<model> <effort>]` first, then the task, `head: <sha>` (read as above), the block, `where the app runs:`, the worktree path, the click path or the approved mock. It writes its pass or fail line with `agent-file.sh check` and reports CHECK PASS or CHECK FAIL: its verdict is evidence, you decide. A fail → send the evidence back to the task manager, stop here. Ask `${CLAUDE_PLUGIN_ROOT}/bin/agent-runtime.sh browser` first:
   - **chrome** — the check deputy drives Claude in Chrome (W5). Every step must match.
   - **headless** — cloud only, the extension can never reach a VM. Here the check deputy runs the same click path with Playwright against the dev server, and saves one screenshot per step as evidence. Same rule: a miss → send the evidence back to the task manager, stop here.
   - **none** — no browser at all. Print the click path under the heading NEEDS HUMAN E2E and stop. Do not merge, do not pass, and never call a path "verified" when nobody drove it. Wait for the human to sign it off.
3. Stop the app server, close whatever ran the click path: the tab, the headless Playwright browser, or nothing if the answer was none. A block that needs the owner's sign (OWNER SIGN of R8) waits for his yes.
4. Run `${CLAUDE_PLUGIN_ROOT}/bin/agent-file.sh todo stage "<name>" merge`, then the gate: `${CLAUDE_PLUGIN_ROOT}/bin/agent-file.sh checks gate "<name>" --dir <worktree path> --branch <branch>`. The task's worktree is gone (W8): gate on a scratch copy of the pushed branch (`git worktree add --detach <scratch> origin/<branch>`, removed after) with `--dir <scratch>` (a remote task too; its reservation on the other machine goes by itself when its process ends); the gate reads the lines gathered into main by `checks gather`. `GATE REFUSED` → no merge: bounce the task with the missing blocks. A remote task (machine not empty): first save the CHECK lines of its REPORT to a file and give the gate `--results <file>`. `GATE PASS` → target working (no target, the default): `Agent` with `subagent_type: merge-deputy`, description `<name> Merge`, it merges into the working branch in the main checkout. Target production: no merge deputy; you run `${CLAUDE_PLUGIN_ROOT}/bin/agent-promote.sh --task "<name>" --branch <branch>` (for a task on another machine add `--results <file>`, its REPORT's CHECK lines saved to a file as above; a local task's lines promote gathers from its worktree itself; no --owner-quote: the words were verified and stored at `todo add --target production`; a short-lived worktree of the production branch; the deploy follows; production is merged back into the working branch at once); then a merge deputy does the rest: `Agent` with `subagent_type: merge-deputy`, description `<name> Merge`, with `merged: <merge hash>` in its brief (the branch, cleanup, worktree line and `todo done`). Brief of the merge deputy, all values:
   ```
   [<model> <effort>]   (yours, from the YOU: line of your start text)
   name: <name>
   session: <task manager | helper | fast-lane>   (fast-lane: a subagent's git worktree, no pane; helper only while the human alone drives it; a Helper that ran helper-join is `task manager`, its pane handle from its line)
   working branch: <the working branch (ap-main-<name>), as the main manager's brief names it>
   production branch: <production_branch of agent_repo.conf, else the target of origin/HEAD, else main>
   machine: <the Orca environment name, empty when the worktree is on this machine>
   branch: <branch>
   worktree path: <path>
   merged: <merge hash>   (target production only: the merge `agent-promote.sh --task` made; else leave empty)
   late yes of: <task>   (a late yes only; else leave empty)
   old branch: <branch>   (a late yes only: the branch the cleanup deletes; else leave empty)
   results file: <path>   (remote task only: the CHECK lines of its REPORT, for the gate's `--results`; else leave empty)
   terminal handle: <term_...>   (orca only, leave empty in plain and cloud)
   todo done arguments: --work <actual> --wait <wait> --bounces <n> --workers <n> --mock <yes|no> --lane <full|fast> --type <t> --tests <n> --adds <n>
   ```
   The numbers come from the report's TIME and FACTS lines (actual = agent work only). A number you do not know → leave that option out, never guess.
   The guard (`bin/agent-guard.sh`) records the merge deputy under the task and, only with the "Rules: Todo before agent" setting on, refuses it when the task line is no longer open, so the todo line stays open until the deputy's own `todo done`.
5. On `MERGE PASS`: `git log --oneline -2`, `git worktree list`, `${CLAUDE_PLUGIN_ROOT}/bin/agent-file.sh show`. All clean → report to the human in H3 shape.
   The merged task leaves `agent-watch.sh --all` by itself (its worktree line goes); no watch to stop.
   Then run `${CLAUDE_PLUGIN_ROOT}/bin/agent-cleanup.sh --apply` (the sweep after every merge, W8).
6. On `MERGE FAIL`: report the first line to the human with the deputy's evidence. Do not retry on your own.
7. Merged a fix early, while its branch is still running? → `SendMessage` that task manager at once: merge its base branch back into your branch (the working branch, or the production branch for a direct fix). Never cherry-pick slices; merge the branch (or its prefix).
8. Every release bumps `version` in `.claude-plugin/plugin.json`; users get nothing without it (no update notice, no auto update).
   Only in the auto-pipeline repo (the one with `bin/agent-release.sh`): after the version bump is committed on the working branch, run `bin/agent-nightly.sh --release-ok` first (exit 1 → `bin/agent-nightly.sh --start` in the background, publish after it is green; no other pre-release run). Then publish with `bin/agent-promote.sh --owner-quote "<his words>" --means "<what you read>"`: it runs `bin/agent-release.sh --push` right after, because users install the `release` branch (the ship set only), not main; merged to production = published.
9. Batch: on `batch <name>: all merged` run `${CLAUDE_PLUGIN_ROOT}/bin/agent-promote.sh --sync` (production into the working branch), then `${CLAUDE_PLUGIN_ROOT}/bin/agent-nightly.sh --start` on the working branch: ONE full suite for the batch. Green → report to the human, the publish needs his verified yes (`agent-promote.sh --owner-quote ... --means ...`). The report repeats the OWNER WORDS lines the gate and promote print, so he sees which words were taken as his yes. Red → `${CLAUDE_PLUGIN_ROOT}/bin/agent-nightly.sh --failures` names the merge of each failing test; a new fixer agent is a normal task: todo add first (the guard needs it), a brief with target, base and both branches, its own PR REVIEW and gate; give it the test, the merge and that task's requirement (a fast-lane deputy or a task manager, by size), never back to the builder; then start the run again (`agent-nightly.sh --start`). It labels each failure "test out of date" (update the test, cite the requirement line or commit) or "real break" (fix the code), as a table: test | merge | task | label | cite or fix. The publish waits until the run is green.
10. URGENT FIX (production is broken): a branch from the production branch, the smallest fix, PR REVIEW and the light related tests; his verified words at dispatch, read as the publish of that task, are his final yes; then `agent-promote.sh --task` (the deploy follows), then merge production back into the working branch (the same command does it, `agent-promote.sh --sync` when it said it waits).
